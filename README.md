# mastodon-custom-charlimit

Nix flake that builds a Mastodon container image **from source**, with the
post character limit raised from 500 to 5000. The image has no distro base,
package manager or shell: it contains Mastodon's runtime closure and a few
small files, and nothing else. CI rebuilds it daily against a fresh nixpkgs,
so fixes to base components (openssl, glibc, libvips, ffmpeg, ...) ship
without waiting for a Mastodon release. It's published as a single multi-arch
(`linux/amd64` + `linux/arm64`) image on ghcr.io.

## How it works

Two independent pins:

- **`flake.lock` → nixpkgs (`nixos-unstable`)** supplies the toolchain and
  every runtime library. Bumping it is the "update base components" step.
- **`mastodon/` → Mastodon itself**: `source.nix` (tag + source hash),
  `gemset.nix` (every gem from `Gemfile.lock`, via bundix) and
  `missing-hashes.json` plus the yarn offline cache hash. Generated by
  `nix run .#update-mastodon`, never edited by hand.

`nix/mastodon.nix` builds Mastodon with nixpkgs' own recipe
(`pkgs/by-name/ma/mastodon/package.nix`, designed to be overridden for
custom versions) but with this repo's pins, so the Mastodon version never
waits on nixpkgs. The toolchain is set in `flake.nix`:

- **Ruby 4.0**, following upstream's `.ruby-version`.
- **Node 26**, newer than upstream's `.nvmrc` (24) but inside the `>=22`
  range both `package.json` files declare.
- **Yarn** from nixpkgs, which must be at least upstream's `packageManager`
  version. Yarn bakes compatibility patches for some dependencies (e.g.
  TypeScript) into each release, so an older one can fail on Mastodon's
  dependencies. If nixpkgs falls behind, override `yarn-berry` in
  `flake.nix`'s `toolchain`.

`checks.toolchain` fails if a Mastodon bump changes the Ruby line, raises
the minimum Node version past ours, or pins a newer Yarn than nixpkgs has.

nixpkgs' recipe takes the toolchain as versioned arguments (`ruby_3_4`,
`nodejs-slim_24`, ...) that it renames as it moves on; `nix/mastodon.nix`
looks up the current names and fails evaluation if they can't be found.

Because Nix outputs are content-addressed, a nixpkgs bump rebuilds exactly
what depends on the changed libraries. Everything generic comes from
cache.nixos.org; CI only compiles the Mastodon-specific parts (native gems,
`assets:precompile`).

`nix/image.nix` turns the result into an OCI image with
[nix2container](https://github.com/nlewo/nix2container): one layer per store
path (up to 100), so registries dedupe unchanged paths, and no image tarball
is ever written to the Nix store.

### What's trimmed from the image

Only gems: `nix/mastodon.nix` installs just the `default`, `production` and
`opentelemetry` Bundler groups, matching upstream's
`without "development test"`, and the image sets `BUNDLE_WITHOUT` to match.
Everything else is stock nixpkgs.

### The character limit

Mastodon's limit comes from a single constant:
`app/validators/status_length_validator.rb`'s `MAX_CHARS`. It enforces the
limit server-side and is what `/api/v2/instance` reports as
`configuration.statuses.max_characters`, which the web UI reads at runtime.
So patching that one line is enough.

`patches/status-length-validator-max-chars.patch` is applied to the source
with fuzz 0, so a Mastodon bump that moves the surrounding code fails the
build loudly rather than half-applying. The build then asserts the end
state (`MAX_CHARS = 5000`), and `checks.patched-syntax` runs `ruby -c` on
the patched file.

To change the limit, edit `maxChars` in `flake.nix`.

Two caveats this can't do anything about:

- Remote servers won't reject your longer posts. `StatusLengthValidator`
  early-returns on non-local statuses, so they federate and display in full.
- Third-party clients that hardcode 500 rather than reading
  `max_characters` from the instance API will still cap you at 500.

## Using the image

```
ghcr.io/e1senh0rn/mastodon:v4.6.6-20260925.17   # immutable: version-date.run
ghcr.io/e1senh0rn/mastodon:v4.6.6               # moves with daily rebuilds
ghcr.io/e1senh0rn/mastodon:latest
```

In a Helm chart, pin the immutable tag or the `@sha256:` digest; both are in
each CI run's summary. After the first publish, check the package's
visibility under the GitHub profile's Packages tab. If it's private, make it
public or give the chart an `imagePullSecrets` entry with a `read:packages`
token.

One image runs all three processes:

| Process | Command |
|---|---|
| Web | *(default)* `puma -C config/puma.rb` |
| Sidekiq | `bundle exec sidekiq` (or `sidekiq`) |
| Streaming | `node ./streaming` |
| Admin | `bin/tootctl ...`, `bin/rails ...` |

Differences from upstream's image to account for:

- Runs as `991:991`; the working directory is the Mastodon store path, and
  `/opt/mastodon` is a symlink to it.
- Local media uploads go to `/tmp/mastodon/public-system`: throwaway, so a
  bare `docker run` works but loses media with the container. For real
  deployments mount a persistent volume there (owned by 991), or use object
  storage. Don't change `PAPERCLIP_ROOT_PATH`: Mastodon serves uploads from
  `public/system`, a symlink to that fixed path baked into the read-only
  package (`uploadsDir` in `flake.nix`).
- `RAILS_SERVE_STATIC_FILES=true` by default, like upstream's image: a
  reverse proxy can't serve `public/` from the image's store path.
- `tini` is the entrypoint, like upstream. In Kubernetes set `args:`, not
  `command:`, or it's bypassed.
- There's no shell, `curl` or `wget`, so healthchecks must be HTTP probes
  (`/health` on 3000, `/api/v1/streaming/health` on 4000), not `CMD` ones.
  Sidekiq touches `/tmp/$MASTODON_SIDEKIQ_READY_FILENAME` once ready, as
  upstream.
- `jemalloc` is preloaded (`LD_PRELOAD`) with upstream's `MALLOC_CONF`.

For Kubernetes, [`charts/mastodon`](charts/mastodon/README.md) deploys the
image with all of the above taken care of.

## Building locally

Needs a Linux builder. On a Mac, Determinate Nix's built-in Linux builder
handles both `aarch64-linux` and `x86_64-linux` (the latter under Rosetta,
slower).

```
nix build .#packages.aarch64-linux.image
nix build .#packages.x86_64-linux.image
```

The result is a small JSON description of the image. The layers are
ordinary store paths. To load it into a local Docker daemon (follows the
active `docker context`, e.g. OrbStack):

```
nix run .#load-arm64                     # -> mastodon:<version>-arm64
nix run .#load-amd64 -- mastodon:test    # custom tag; run with --platform linux/amd64
scripts/smoke-test.sh mastodon:<version>-arm64
```

The smoke test boots the image against throwaway Postgres and Redis and
checks web, streaming, Sidekiq, the character limit, static files, uploads
and the media conversions Mastodon runs.

Or push a single-arch image straight to a registry (`skopeo login ghcr.io`
first):

```
nix run .#push-arm64 -- ghcr.io/e1senh0rn/mastodon:dev-arm64
```

For multi-arch tags, let CI do it so both architectures come from one
commit.

`nix flake check` runs the validator syntax and toolchain checks (needs a
Linux builder).

## Bumping versions

**Base components** (nixpkgs: glibc, openssl, Ruby, Node, libvips,
ffmpeg, ...):

```
nix run .#update-base
nix run .#update-base -- --commit-lock-file   # extra args go to `nix flake update`
```

This bumps only the `nixpkgs` input and prints the old and new revision.
CI does this daily. Gems and npm packages aren't base components: they're
pinned by Mastodon's lockfiles and move with `update-mastodon`.

**Mastodon**:

```
nix run .#update-mastodon               # latest patch release of the pinned major.minor
nix run .#update-mastodon -- v4.8.0     # a specific tag, e.g. to move to a new minor
```

This regenerates `mastodon/` in place (atomically; a failed run leaves it
untouched). It uses the same steps as nixpkgs' own `update.sh`, against this
flake's pinned nixpkgs. It doesn't check that the patch still applies;
`nix build` does that and fails loudly if not.

## CI

`.github/workflows/build.yml` runs the whole cycle: update pins, build
both architectures, smoke-test, publish, commit the updated pins, and pin
and release the Helm chart. Which steps run depends on the trigger:

| Trigger | Update Mastodon | Update nixpkgs | Build + test | Publish | Commit pins | Chart |
|---|---|---|---|---|---|---|
| Manual (`gh workflow run build.yml`) | input | input | yes | input | input | with publish |
| Daily 03:17 UTC (**disabled**, see below) | yes | yes | yes | yes | yes | yes |
| Push to `main` | – | – | yes | yes | – | yes |
| Pull request | – | – | yes | – | – | – |

"Chart" pins `charts/mastodon` to the published `:latest`, bumps its
version, commits, and releases it via `.github/workflows/chart.yml`; see
the chart README's "Releases". `chart.yml` also lints the chart on pull
requests (and requires a version bump when it changed) and releases chart
changes pushed to `main`.

Manual inputs all default to on, so a bare `gh workflow run build.yml` does
the full cycle. Turn parts off as needed:

```
gh workflow run build.yml                                   # everything
gh workflow run build.yml -f update_mastodon=false          # base components only
gh workflow run build.yml -f update_base=false              # Mastodon only
gh workflow run build.yml -f publish=false -f commit=false  # just try a fresh nixpkgs
gh workflow run build.yml -f mastodon_version=v4.8.0        # a specific release, e.g. a new minor
gh workflow run build.yml -f force=true                     # rebuild/republish an unchanged image
```

"Update Mastodon" moves to the latest patch release of the pinned
major.minor, never to a new minor (those bring migrations and upgrade steps
to run on the instance) and never backwards. Bump the minor deliberately
with `mastodon_version`. It's a quick no-op when the latest patch is
already pinned.

Publishing only happens from the default branch. A manual run on another
branch with `publish` on just builds and smoke-tests, with a warning.

Each architecture builds natively (`ubuntu-26.04` and `ubuntu-26.04-arm`)
and pushes an arch-suffixed tag. A final job combines them into the
multi-arch tags, annotated with the git commit and nixpkgs revision. Those
are deliberately kept out of the per-arch images, so an image only differs
when its contents do. The index also records its immutable tag, which is
how the chart finds the build behind `:latest`. The arm64 runner is free for public repos; for a
private one, point the `ARM64_RUNNER` repo variable at a larger or
self-hosted arm64 runner.

Actions are referenced by version tag and locked to commits in
`.github/workflows/actions.lock`; a run fails if an action's commit doesn't
match. Regenerate it with `gh actions-lock` (the `github/gh-actions-lock`
extension) after adding or changing a `uses:`, and check it with
`gh actions-lock --verify`. Never edit it by hand. Dependabot
(`.github/dependabot.yml`) proposes updates weekly and updates the lockfile
in the same PR.

When publishing, whether anything changed is decided before building. The
Nix output paths of both images are evaluated (no build needed) and
compared with a fingerprint annotation on the published `:latest`. If
they're identical, build and publish are skipped. That includes a nixpkgs
bump that touches nothing in the image, and a push that only changes the
workflow (use `-f force=true` to exercise the build and publish anyway). With `publish=false` the
build always runs, since then the build is the point.

Updated pins are committed back to the branch the workflow ran on, but only
once they're proven: built and smoke-tested, and published if publishing
was on. If the build or smoke test fails, for example because a new
Mastodon version no longer takes the char-limit patch, nothing is
committed. Re-run with `-f update_mastodon=false` to still get the
base-component updates.

The schedule is **disabled for now**: the `schedule:` trigger is commented
out. Uncomment it to turn the daily runs on. Manual, push and pull-request
runs aren't affected.

Optional: set a `CACHIX_NAME` repo variable and `CACHIX_AUTH_TOKEN` secret
to cache the Mastodon-specific builds between runs.
